## 1. Bug Categories — Beyond "Existing"

The system must classify every finding into one of 10 categories. Currently it has none of this.

```python
class BugCategory(str, Enum):
    EXISTING = "existing"            # Present and triggerable right now
    LATENT = "latent"                # Present but requires specific conditions to manifest
    REGRESSION = "regression"        # Introduced between versions (was working, now broken)
    FIX_INDUCED = "fix_induced"      # Would be introduced by proposed fix for another bug
    MUTATION_SURVIVING = "mutation"  # Undetected by existing test suite (no test covers this boundary)
    SCALE_DEPENDENT = "scale"        # Manifests only under load/concurrency (works at N=10, breaks at N=10000)
    DEPENDENCY = "dependency"        # In external library, not in the project's own code
    CONFIGURATION = "config"         # Environment-specific (production only, specific OS, specific DB version)
    TEMPORAL = "temporal"            # Time-dependent (works now, breaks at midnight/end of month/leap year)
    PROBABILISTIC = "probabilistic"  # Non-deterministic (race condition with 12% failure rate)
```

**How each category is detected**:

| Category | Detection Method | Layer Required |
|----------|-----------------|----------------|
| EXISTING | CPG taint + agent analysis + sandbox PoC | Base system |
| LATENT | Symbolic executor finds path → sandbox confirms with computed input | Layer 2 |
| REGRESSION | Differential analysis: behavior changed between versions | Layer 4 |
| FIX_INDUCED | Fix impact analysis: caller behavior changes after proposed fix | Layer 12 |
| MUTATION_SURVIVING | Test suite passes against mutation → untested boundary | Layer 9 |
| SCALE_DEPENDENT | Sandbox runs at 1x, 10x, 100x, 1000x scale → behavior diverges | Layer 8 (invariant at scale) |
| DEPENDENCY | Dependency scanner checks `requirements.txt` against NVD/CVE database | New module needed |
| CONFIGURATION | Sandbox runs under multiple configs → behavior differs | Layer 4 (differential) |
| TEMPORAL | Sandbox runs with system clock at boundary values (midnight, Feb 29, 2038) | New module needed |
| PROBABILISTIC | Statistical re-execution (100 runs) → failure rate 5-95% | Base system (execute_statistical) |

## 2. Proof System — 7 Types, Ranked by Strength

A bug is not "confirmed" by agent opinion. It is confirmed by proof. Multiple proof types increase confidence multiplicatively.

### Proof Types

| # | Proof Type | Generated By | What It Proves | Strength | Evidence Format |
|---|-----------|-------------|----------------|----------|----------------|
| 1 | **Sandbox Execution** | Agent submits PoC, sandbox runs | "This input triggers this behavior" | 0.80 | `ExecutionReceipt` with exit code, stdout, stderr, duration |
| 2 | **Symbolic Proof** | Concolic executor solves path constraints | "This exact input reaches this line with mathematical certainty" | 1.00 | SMT solver output with constraint set + satisfying assignment |
| 3 | **Invariant Violation** | Specification miner detects broken contract | "This function violates its observed invariant across 10K inputs" | 0.90 | Invariant statement + violating input + confidence interval |
| 4 | **Fuzzer Crash** | Fuzzer generates crashing input | "This random input triggers a crash" | 0.70 | Crash triage: stack trace hash, input bytes, coverage info |
| 5 | **Mutation Survivor** | Test suite passes against mutated code | "This boundary has zero test coverage" | 0.50 | Mutation applied, surviving test count, coverage gap report |
| 6 | **Differential Proof** | Two executions produce different outputs | "Version A and B behave differently for the same input" | 0.85 | Input, output_A, output_B, diff, environment metadata |
| 7 | **Sanitizer Report** | ASAN/UBSAN/TSAN catches at runtime | "Memory corruption/undefined behavior detected at this address" | 0.95 | Sanitizer output with address, size, allocation site, free site |

### Confirmation Thresholds

| Status | Requirement |
|--------|------------|
| **SUSPECTED** | 0 proofs. Agent claim only. Not escalated to Bench. |
| **UNDER INVESTIGATION** | ≥1 proof with strength ≥ 0.5. Escalated to Bench for review. |
| **CONFIRMED** | ≥1 proof with strength ≥ 0.80. Accepted by Bench consensus. |
| **FULLY CHARACTERIZED** | ≥3 proofs from different types AND complete trigger matrix (≥5 rows, ≥3 layers). |

## 4. Post-Judge Lifecycle — Full Flow

### 4.1 Judge Confirms Bug

```
JUDGE CONFIRMS
│
├─→ Finding status set to CONFIRMED in evidence graph
│     └─ Immutable. Cannot be changed without human override.
│
├─→ Trigger Matrix populated from all contributing layers
│     └─ Minimum 5 rows from ≥3 layers before bug can be marked FULLY_CHARACTERIZED
│
├─→ Chain Detection runs
│     ├─ Query: does this bug ENABLE any other confirmed bug?
│     ├─ Query: is this bug ENABLED BY any other confirmed bug?
│     ├─ If chain found → combined severity = max(all members)
│     └─ Chain finding created with all member bugs linked
│
├─→ Fix Proposal generated
│     ├─ Agent or Judge authors fix
│     ├─ Fix Impact Analysis runs (Layer 12)
│     │     ├─ CPG traces all callers of changed function
│     │     ├─ Simulates behavior change for each caller
│     │     └─ Flags callers whose assumptions are violated
│     ├─ Sandbox validates fix
│     │     ├─ Apply patch to code copy
│     │     ├─ Run existing test suite against patched code
│     │     ├─ Run generated regression test
│     │     └─ All pass → fix VALIDATED
│     └─ Fix stored with finding
│
├─→ Regression Test auto-generated
│     └─ Test ensures bug never returns. Added to test suite.
│
├─→ Export triggered
│     ├─ SARIF export (GitHub Code Scanning)
│     ├─ JSON report (for CI/CD)
│     └─ Notification (Slack/PagerDuty/Jira based on severity)
│
├─→ Learning system updated
│     ├─ Bug Pattern DB: embedding of code snippet stored
│     ├─ ML model: retrained with new confirmed bug
│     ├─ Hotspot score: affected file incremented
│     └─ Agent credibility: finding agent's trust_score increased
│
└─→ Re-scan scheduled
      └─ After fix merged, CI triggers re-scan to verify bug is gone
```

### 4.2 Judge Dismisses Bug

```
JUDGE DISMISSES
│
├─→ Finding status set to DISMISSED in evidence graph
│     └─ Immutable. Can be challenged via human override.
│
├─→ Dismissal reason recorded
│     ├─ false_positive: agent hallucinated, no real bug
│     ├─ not_exploitable: bug exists but can't be triggered
│     ├─ out_of_scope: bug is in dead code or non-production path
│     ├─ already_fixed: bug was patched in a later commit
│     └─ insufficient_evidence: not enough proof to confirm
│
├─→ Agent credibility adjusted
│     ├─ False positive → agent's hallucination_rate increased
│     └─ If rate > 40% → agent ejected from swarm
│
├─→ Judge calibration updated
│     ├─ If human later overrides dismissal → judge FNR increased
│     └─ Fed into calibration loop for future runs
│
├─→ Dismissal logged for audit
│     └─ Immutable audit trail entry with judge reasoning
│
└─→ If human overrides dismissal
      ├─ Finding re-opened with escalated priority
      ├─ Additional investigation requested
      └─ Re-escalated to Bench with override annotation
```

### 4.3 Judge Deadlocks (2-2-1 Split)

```
JUDGE DEADLOCKS
│
├─→ Tiebreaker Protocol fires (in order):
│
│   Level 1: WEIGHTED RE-VOTE
│     └─ Each judge's vote multiplied by calibration weight
│         weight = 1.0 - false_positive_rate (for confirm votes)
│         weight = 1.0 - false_negative_rate (for dismiss votes)
│     └─ If weighted majority emerges → verdict accepted
│
│   Level 2: EVIDENCE-ONLY RE-VOTE
│     └─ Strip all agent arguments. Send ONLY sandbox receipts,
│         sanitizer reports, fuzzer outputs, and trigger matrix.
│     └─ "Based solely on this evidence, does a confirmed bug exist? Y/N"
│     └─ If majority emerges → verdict accepted
│
│   Level 3: SPECIALIST ESCALATION
│     └─ Bug type determines tiebreaker:
│         security bug → Security Judge breaks tie
│         concurrency → Concurrency Judge breaks tie
│         logic → Logic Judge breaks tie
│         unknown → Architecture Judge breaks tie
│     └─ BUT: if specialist judge's FPR > 0.20 or FNR > 0.20 →
│         authority REVOKED, falls through to next specialist
│
│   Level 4: META-JUDGE
│     └─ Rank 1 model from judge provider (most capable)
│     └─ Receives entire case + all tiebreaker history
│     └─ Casts deciding vote
│     └─ Expensive but only fires when all levels above fail
│
├─→ Conservative Principle applied
│     └─ "When in doubt, escalate severity."
│     └─ If tiebreaker confirms → highest severity among confirming judges
│     └─ Finding annotated: SEVERITY_DISPUTED
│
└─→ Deadlock logged for audit
      └─ Full deadlock history with all tiebreaker attempts
```

### 4.4 Human Override (Any Verdict)

```
HUMAN OVERRIDE
│
├─→ Override justification REQUIRED (cannot be empty)
│
├─→ Severity downgrade (8+ → lower):
│     └─ Dual authorization required (two operators)
│     └─ First override → PENDING_SECOND_APPROVAL
│     └─ Second override → applied
│     └─ Security lead notified via email
│
├─→ Override logged in immutable audit chain
│     ├─ Operator identity
│     ├─ Timestamp
│     ├─ Before/after verdict
│     ├─ Justification text
│     └─ Chain hash (cryptographic linking to previous entries)
│
├─→ Override review queue
│     └─ All overrides visible in TUI "Override Summary" panel
│     └─ Security lead must acknowledge within 72 hours
│
└─→ System learning from override
      ├─ If override reversed a judge dismissal → judge FNR increased
      ├─ If override reversed a judge confirmation → judge FPR increased
      └─ Feeds into judge calibration for future runs
```

## 5. What the Current System Does vs What It Should

| Capability | Current | Should Be |
|-----------|---------|-----------|
| Bug categorization | None — all findings are flat | 10 categories with detection methods per category |
| Proof types | 1 (sandbox receipt) | 7 types ranked by strength (0.50–1.00) |
| Confirmation thresholds | Agent says "verified" → it's verified | 4-tier: suspected → investigating → confirmed → fully characterized |
| Finding schema | 5 fields (claim, location, severity, verified, mechanism) | 14 sections with 50+ fields |
| Post-confirm flow | None — finding stored in memory | Fix proposal → impact analysis → validation → regression test → export → learning |
| Post-dismissal flow | None — finding discarded | Dismissal reason → agent credibility → judge calibration → audit trail |
| Tiebreaker protocol | Simulated with random | 4-level protocol with calibration checks and conservative principle |
| Human override | None | Justification-required, dual-auth for severity 8+, immutable audit chain |
| Fix workflow | None | Agent/judge authors fix → impact analysis → sandbox validation → CI re-scan |
| Learning loop | None — every run is amnesia | Pattern DB updated, ML retrained, hotspot scores, credibility adjusted |
| Notification | None | Slack, PagerDuty, Jira based on severity |
| SLA tracking | None | Severity → response time → responsible team → escalation path |
